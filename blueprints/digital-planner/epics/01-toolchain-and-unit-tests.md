## Conventions that bite in this area

- **Every unit test that touches `lib/webhooks/dispatch.ts` or `lib/google-calendar/sync.ts` mocks
  `@/lib/supabase/server` and `global.fetch`.** Neither module may make a real network call inside
  `tests/unit/**` — that is what `tests/integration/**` (next epic) is for. See
  `.claude/rules/tests.md`.
- **`next lint` with zero ESLint config prompts interactively and hangs a non-interactive run.**
  This repo had no `.eslintrc*` and no `eslint` dependency before `E1-T2` — confirmed by reading
  the repo, not assumed. `E1-T2` exists specifically to close that gap before any CI or Verify
  command relies on `npm run lint`.
- **`eslint-config-next@14.2.35`'s peer range excludes ESLint 9** — it ships an old-style
  `.eslintrc` config, not flat config. `E1-T2` pins `eslint@^8.57.0` for exactly this reason. Both
  pins are marked `UNVERIFIED` in `blueprint.md` §11 — `stack-researcher` did not check them this
  session; re-verify before `npm install` if this epic is executed long after the blueprint date.
- **`next/core-web-vitals` may report pre-existing findings** the first time it runs on this
  never-linted codebase. Only `error`-level findings fail `npm run lint` (warnings do not). If any
  appear, fix them as minimal, non-behavioral changes (missing `key`, unused import) — never
  restructure a component. This blueprint's Non-Goals forbid UI/UX changes.
- **`@testing-library/react` has exactly one call site in this epic** — the second assertion in
  `E1-T3`'s smoke test. It exists to prove the full toolchain renders and queries a component, not
  because this blueprint adds component tests elsewhere (it deliberately does not — see
  `blueprint.md` §13, "What is deliberately not tested").

### `E1-T1` — Bump Node target to 22 and add typecheck script

**Depends on:** nothing · **Priority:** p0 — blocks every later task, jsdom (`E1-T3`) requires
Node `^22.22.2 || ^24.15.0 || >=26.0.0`

Bump `@types/node` to `^22` (`npm install -D @types/node@^22`). Add `"engines": { "node": "22.x" }`
to `package.json` — this is what Vercel's build platform reads to select the Node major (see
`blueprint.md` §12), and it documents the same requirement `actions/setup-node` enforces in CI. Add
a `"typecheck": "tsc --noEmit"` script — the project had none; every later task's Verify and the
global gate use it. Add `"blueprints"`, `"vitest.config.ts"` and `"vitest.setup.ts"` to
`tsconfig.json`'s `exclude` array (currently `["node_modules"]` only).

Two distinct reasons, both confirmed by running this step live:
- `"blueprints"` — the bundle at `blueprints/digital-planner/workspace/` ships `.ts` files that
  `tsc`'s default `include: ["**/*.ts", ...]` would otherwise type-check as a redundant second copy.
- `"vitest.config.ts"` / `"vitest.setup.ts"` — Bootstrap drops them at the project root *before*
  this task, but the packages they import (`@vitejs/plugin-react`, `vitest/config`,
  `@testing-library/jest-dom`) do not arrive until `E1-T3`. Without the exclusion this task's own
  `npm run typecheck` gate fails with `TS2307: Cannot find module` on files it never wrote. They
  also belong outside the app typecheck permanently: Vite transpiles them itself, and the app's
  `tsc --noEmit` should not depend on test devDependencies.

**Files**
- `package.json` — edit: bump `@types/node`, add `engines`, add `typecheck` script
- `package-lock.json` — edit: regenerated by `npm install`
- `tsconfig.json` — edit: add `"blueprints"` to `exclude`

**Acceptance**

1. **WHEN** `package.json` is inspected **THE SYSTEM SHALL** declare `"@types/node"` matching `^22`
   under `devDependencies`.
2. **WHEN** `package.json` is inspected **THE SYSTEM SHALL** declare
   `"engines": { "node": "22.x" }`.
3. **WHEN** `package.json` is inspected **THE SYSTEM SHALL** declare a `"typecheck"` script equal
   to `"tsc --noEmit"`.
4. **WHEN** `tsconfig.json`'s `exclude` array is inspected **THE SYSTEM SHALL** contain
   `"blueprints"`, `"vitest.config.ts"` and `"vitest.setup.ts"` — the latter two because Bootstrap
   places them at the project root before this step while the packages they import are not
   installed until `E1-T3`.
5. **WHEN** `npm run typecheck` runs **THE SYSTEM SHALL** exit 0 against the existing, untouched
   application code.

**Verify**

```bash

node -e "const p=require('./package.json'); if(p.engines?.node !== '22.x') process.exit(1)"
```

### `E1-T4` — Unit tests for webhook HMAC signing (`lib/webhooks/dispatch.ts`)

**Depends on:** `E1-T3` · **Priority:** p0

Create `tests/unit/webhooks/dispatch.test.ts`. Mock `@/lib/supabase/server`'s exported
`createServiceClient` (`vi.mock`) to return a fake chainable client whose
`.from('webhook_configs').select().eq('active', true)` resolves to one fixture row —
`{ id: 'wh-1', url: 'https://example.com/hook', secret: 'test-secret-please-ignore', active: true,
events: ['pieza_aprobada'] }` — and whose `.from('webhook_deliveries').insert(...)` is a
`vi.fn()` you can assert on. Mock `global.fetch` with `vi.fn()`. Build the payload with the real,
unmocked `buildWebhookPayload('pieza_aprobada', fixturePiece, 'Ana Agencia', baseUrl, 'Marca X')`
and pass it to the real, unmocked `dispatchWebhookEvent`. Compute the expected signature inside the
test with Node's `crypto.createHmac('sha256', 'test-secret-please-ignore')` over
`JSON.stringify(payload)` — the same serialization `dispatchWebhookEvent` performs internally.

**Files**
- `tests/unit/webhooks/dispatch.test.ts` — new

**Acceptance**

Copied verbatim from `tasks.json`'s `E1-T4.acceptance`:

1. **WHEN** `dispatchWebhookEvent` is called with a payload built by
   `buildWebhookPayload('pieza_aprobada', ...)` and one mocked active webhook config matching that
   event **THE SYSTEM SHALL** call `fetch` exactly once with header `X-Planner-Signature` equal to
   the HMAC-SHA256 hex digest of the exact JSON body, computed independently in the test using the
   same webhook secret.
2. **WHEN** the same call is made **THE SYSTEM SHALL** call `fetch` with header `X-Planner-Event`
   equal to `pieza_aprobada` and header `Content-Type` equal to `application/json`.
3. **WHEN** the mocked `fetch` resolves with `status: 200` **THE SYSTEM SHALL** insert one mocked
   `webhook_deliveries` row with `response_status: 200` and `error: null`.
4. **WHEN** a mocked webhook config's `events` array does not include the dispatched event type
   **THE SYSTEM SHALL NOT** call `fetch` for that config.
5. **WHEN** the mocked `fetch` rejects with a network error **THE SYSTEM SHALL** insert a
   `webhook_deliveries` row with `response_status: null` and `error` equal to the thrown error's
   message, and **SHALL NOT** throw out of `dispatchWebhookEvent`.

### `E1-T5` — Unit tests for timezone-consistent date handling (`lib/date-utils.ts`, `lib/tz.ts`)

**Files**

## Pitfalls

- **Mocking `@/lib/supabase/server` with the wrong export shape silently no-ops the test.** The
  module exports both `createClient` (cookie-based) and `createServiceClient` (service role,
  no cookies). `dispatchWebhookEvent` and `syncPieceToGoogleCalendar` call `createServiceClient`
  only — mock that one, not `createClient`.
- **`next/core-web-vitals` is a warning-tolerant gate, not a zero-findings gate.** Do not chase
  every warning in `E1-T2` — only `error`-level findings block `npm run lint`.
- **`jsdom@^30.1.1` requires Node `^22.22.2 || ^24.15.0 || >=26.0.0`.** If `E1-T1` is skipped or the
  build machine is on an older Node 22 patch, `E1-T3`'s install or first run fails with a resolution
  or runtime error that looks unrelated to Node version — check `node -v` first.
